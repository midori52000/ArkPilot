## Recommended approach

### 首版范围

首版先做“后端能力透出 + 宿主消费闭环”，不追求一次覆盖文档里的全部矩阵：

1. **Layer 1 首批落地**：只覆盖 `FunctionCallOutput` / `CustomToolCallOutput` 的规则式微压缩。
2. **Layer 2 打通状态**：复用现有 memories 管线，先把 `memory_mode`、polluted、forgetting、summary preview、尾部保留策略接出来。
3. **Layer 3 打通观测**：继续复用 compact 主链，只补 trigger source、saved tokens、rebuild 状态、artifact refs。
4. **Layer 4 打通边界**：显式 failure count、circuit breaker、排除名单；ArkTS fallback 只做兜底。
5. **UI 首版只解释状态**：不做 memory 编辑器、独立 context 设置页、复杂诊断页。

### 第二批再做

- 把 Layer 1 扩到 `LocalShellCall`、`ToolSearchOutput`、web、MCP 大 JSON、diff/write 结果。
- 增加 memory 明细查看、人工清理或编辑。
- 增加 richer replay/artifact 诊断界面。
- 如果后端后续提供稳定写入口，再考虑极少量 context 配置项写回。

## Implementation steps

### Phase 1 — 先锁 Layer 1 历史项契约，避免后面 UI/host 返工

#### 目标
把“哪些工具结果可以被微压缩、删完后如何追溯、哪些边界不能动”收敛为 core/history 的事实，而不是 ArkTS 的展示推断。

#### 关键文件
- `codex-main/codex-rs/core/src/context_manager/history.rs`
- `codex-main/codex-rs/core/src/codex.rs`
- 如已有相邻类型定义文件，按现有 history item 结构补充即可

#### 优先复用
- `record_items(...)`
- `get_total_token_usage(...)`
- `get_total_token_usage_breakdown(...)`

#### 具体步骤
1. 给历史项补最小元信息，只补首版真正要用到的字段：
   - `item_kind`
   - `source_kind`
   - `group_id` / `message_id`
   - `tool_call_id` / `tool_name`
   - `is_compactable`
2. 给工具结果补稳定的 replay 契约，优先直接挂在现有 metadata 上，不引入新存储：
   - `replayKey`
   - `compacted`
   - `artifactRef` 或等价 locator
3. 首版只对白名单工具结果做**规则式字段删减**，不做模型摘要：
   - 只压旧的、可再取的、低信息密度结果
   - 不动 `user` / `assistant` 正常消息
   - 不动当前 turn、pin 区、最近关键工作集
4. 保证结构边界：
   - `tool_use` / `tool_result` 成对保留或成对压缩
   - 同一 `message_id` 下的碎片整体处理
5. 让 token 统计继续走现有总量计算链，确保压缩后数字与历史口径一致。

#### Done 定义
- `record_items(...)` 写入后的历史能够稳定识别首批可压缩工具结果。
- 压缩后仍保留可追溯 locator。
- token usage 会随微压缩下降，且不破坏现有历史规范化。

### Phase 2 — 扩 host snapshot 与 payload，把四层状态透给 ArkTS

#### 目标
不新开 endpoint，直接扩现有 host 桥接，让 ArkTS 从 `thread/read`、`turn/poll`、runtime snapshot 拿到 context-management 状态。

#### 关键文件
- `codex-main/codex-rs/ohos-host/src/lib.rs`

#### 优先复用
- `ThreadContextSnapshot`
- `load_thread_context_snapshots(...)`
- `persist_thread_context_snapshots(...)`
- `build_thread_read_payload(...)`
- `build_turn_poll_payload(...)`

#### 具体步骤
1. 扩 `ThreadContextSnapshot`，继续复用 `runtime/thread-context.json`，不要新建 runtime 文件：
   - `last_micro_compaction_at`
   - `last_micro_compaction_item_count`
   - `last_micro_compaction_saved_tokens`
   - `memory_mode`
   - `memory_summary_updated_at`
   - `memory_summary_preview`
   - `compaction_failure_count`
   - `compaction_circuit_open`
   - `last_full_compaction_trigger`
   - `last_full_compaction_rebuilt_artifact_count`
   - `recent_artifact_refs`
2. 扩 `build_thread_read_payload(...)`，新增 `contextManagement` 节点，作为线程恢复态事实来源。
3. 扩 `build_turn_poll_payload(...)`，把当前 turn 相关的 micro/memory/full/circuit 状态也透出来，作为轮询兜底态事实来源。
4. 所有新增字段先保持 optional，保证旧数据和未升级前端都能兼容。

#### Done 定义
- 应用重启后 `thread/read` 仍能恢复最近一次 context-management 状态。
- turn 进行中仅靠 `turn/poll` 也能看到后端状态。
- 没有新状态时返回默认值/空对象，不破坏旧逻辑。

### Phase 3 — ArkTS backend 只承载这些状态，不重写策略

#### 目标
把 host 新字段接入现有 `CodexBackendSnapshot` / `CodexThreadRecord` / snapshot 订阅链，继续复用 event/poll/reconcile 模式。

#### 关键文件
- `Agent/entry/src/main/ets/backend/ConsoleModels.ets`
- `Agent/entry/src/main/ets/backend/CodexBackend.ets`
- `Agent/entry/src/main/ets/backend/CodexNative.ets`

#### 优先复用
- `CodexBackendSnapshot`
- `CodexThreadRecord`
- `applyTokenUsagePayload(...)`
- `readThreadSnapshot(...)`
- `applyTurnPollResult(...)`
- 现有 snapshot subscribe/notify 链

#### 具体步骤
1. 在 `ConsoleModels.ets` 中增加轻量 context-management 模型；优先用一个聚合对象，而不是把字段散落到 `TurnTokenUsage`：
   - `microCompaction`
   - `memory`
   - `fullCompaction`
   - `circuitBreaker`
2. 给 `CodexBackendSnapshot` 增加 `contextManagement` 字段；保留现有 `compaction` 字段给完整压缩 notice 复用。
3. 给 `CodexThreadRecord` 增加最小缓存字段，保存最近一次 host 下发的 context-management 状态。
4. 在三条现有状态流统一消费：
   - `thread/read`：页面恢复
   - `turn/poll`：轮询兜底
   - event/reconcile：实时与尾包修正
5. 不把 Layer 1/2/3/4 判定逻辑搬到 ArkTS，只做状态合并和显示。

#### Done 定义
- 重新进入页面、恢复会话、turn 轮询都能看到一致状态。
- 新状态不需要独立 service，就能跟当前 backend snapshot 一起刷新。

### Phase 4 — 复用 memories 管线，先把 Layer 2 状态打通

#### 目标
ArkPilot 不自己做 memory 提炼器，只消费 codex 现有 stage1/phase2/memory_mode 结果，并把“长期事实”与“近期原始尾部保留”拆开。

#### 关键文件
- `codex-main/codex-rs/state/src/runtime/memories.rs`
- `codex-main/codex-rs/core/src/memories/phase1.rs`
- `codex-main/codex-rs/core/src/memories/phase2.rs`
- `codex-main/codex-rs/core/src/stream_events_utils.rs`
- `codex-main/codex-rs/core/src/mcp_tool_call.rs`
- `codex-main/codex-rs/ohos-host/src/lib.rs`
- `Agent/entry/src/main/ets/backend/CodexBackend.ets`

#### 优先复用
- `record_stage1_output_usage(...)`
- `claim_stage1_jobs_for_startup(...)`
- `mark_thread_memory_mode_polluted(...)`

#### 具体步骤
1. 让 host 把 `memory_mode`、最近 memory 更新时间、preview、forgetting 是否刚发生透给 ArkTS。
2. 对 WebSearch / MCP 造成的 polluted，继续以 core/state 为事实来源；ArkTS 只展示，不自行判断。
3. 用现有 memory 管线做长期事实，近期原始上下文则通过 runtime 尾部保留策略解决，二者不要混成同一概念。
4. 继续复用 `record_stage1_output_usage(...)` 记录 memory 被引用的 usage，不新建另一套 usage 统计。

#### Done 定义
- `enabled / disabled / polluted` 在 ArkTS 可见。
- forgetting 后的状态变化可从 host/UI 观察到。
- 尾部保留策略不依赖新的持久化层。

### Phase 5 — 继续复用 compact 主链，只补 Layer 3 的战后重建观测

#### 目标
完整压缩仍走 codex 后端现有主链，ArkTS 只拿结果与恢复状态，不碰 compact prompt 与算法。

#### 关键文件
- `codex-main/codex-rs/core/src/compact.rs`
- `codex-main/codex-rs/core/src/codex.rs`
- `codex-main/codex-rs/core/src/codex/rollout_reconstruction.rs`
- `codex-main/codex-rs/ohos-host/src/lib.rs`
- `Agent/entry/src/main/ets/backend/CodexBackend.ets`

#### 优先复用
- `pre_compress_tool_outputs(...)`
- `run_pre_sampling_compact(...)`
- `maybe_run_previous_model_inline_compact(...)`
- `run_auto_compact(...)`
- `run_inline_auto_compact_task(...)`
- `replace_history(...)`
- `reference_context_item(...)`

#### 具体步骤
1. 在 full compaction 结果里补齐首版真正需要展示的字段：
   - `triggerSource: manual | pre_turn | mid_turn | model_switch`
   - `providerMode: local | remote`
   - `savedTokens`
   - `trimmedItemCount`
   - `rebuiltArtifactCount`
   - `referenceContextReestablished`
2. 这些字段先通过 host snapshot / payload 透出，供 ArkTS notice 与 token card 复用。
3. `recent_artifact_refs` 首版只保留少量关键引用，作为战后重建状态与后续 reinject 的支撑，不做独立 artifact 系统。

#### Done 定义
- 用户能看出“已完整压缩”与“已压缩并重建工作上下文”的区别。
- model switch / pre-turn / mid-turn 三种 trigger 在宿主侧可区分。

### Phase 6 — 收口 Layer 4：自动触发、熔断、宿主兜底边界

#### 目标
自动化只在后端可观测之后再接，避免 ArkTS 与 Rust 双方各做一套调度。

#### 关键文件
- `codex-main/codex-rs/core/src/codex.rs`
- `codex-main/codex-rs/ohos-host/src/lib.rs`
- `Agent/entry/src/main/ets/backend/CompactionPolicy.ets`
- `Agent/entry/src/main/ets/backend/CodexBackend.ets`

#### 优先复用
- `run_pre_sampling_compact(...)`
- `maybe_run_previous_model_inline_compact(...)`
- `run_auto_compact(...)`
- `shouldStartCompaction(...)`（ArkTS fallback）

#### 具体步骤
1. 后端补显式 failure count、circuit breaker、cooldown 状态，并通过 host 透出。
2. 明确自动压缩排除名单：
   - memory job
   - compact job
   - 已在 compaction turn 中
   - 当前 turn 仍在活跃
   - 无 context window / 无阈值
3. 保留 `CompactionPolicy.ets`，但只作为**后端状态不可得时**的 fallback；不要把四层统一策略塞进 ArkTS。
4. 同一 turn 的自动压缩设上限，避免 pre-turn / mid-turn 套娃。

#### Done 定义
- 连续失败达到阈值后自动熔断。
- 手动重试成功后可清零 failure count 并恢复自动链。
- ArkTS 不会在后端已自动处理时重复触发 fallback compaction。

### Phase 7 — UI 只做解释层，复用现有卡片与 notice

#### 目标
让用户能看懂系统当前在第几层工作，但不新增复杂页面。

#### 关键文件
- `Agent/entry/src/main/ets/pages/Index.ets`
- 如需要少量文案或模型定义，再补 `ConsoleModels.ets`

#### 优先复用
- `applyCompactionSnapshot(...)`
- `upsertCompactionNotice(...)`
- `tokenUsageCard()`
- `approvalCard(...)`
- `requestUserInputCard(...)`

#### 具体步骤
1. 在 token/context card 中增加一块轻量状态摘要：
   - 已微压缩 / 待微压缩
   - memory enabled / polluted
   - 已完整压缩 / 已重建
   - 熔断中 / 等待手动重试
2. 继续复用现有 compaction notice 展示完整压缩进度与结果。
3. 最近一次动作展示只做短文本解释：节省了多少 token、删减了多少项、触发源是什么。
4. 首版不新增设置页，不新增 memory 编辑页。

#### Done 定义
- 不打开新页面也能从主工作台看懂当前 context-management 状态。
- 页面恢复后状态仍能从 backend snapshot 还原。

## Verification

### 1. Rust/history 层验证
- 为 Layer 1 白名单工具结果补单元测试：确认大字段被删减、locator 仍保留、`tool_use/tool_result` 边界不破。
- 验证压缩前后 `get_total_token_usage(...)` / breakdown 的统计口径一致。

### 2. Rust host 契约验证
- 为 `ThreadContextSnapshot` 做旧文件兼容验证。
- 为 `build_thread_read_payload(...)` / `build_turn_poll_payload(...)` 做序列化测试，确认 `contextManagement` 缺省可用。

### 3. memory / polluted 验证
- 触发 WebSearch 或 MCP 污染路径，确认 `mark_thread_memory_mode_polluted(...)` 后状态能经 host 透出到 ArkTS。
- 验证 `record_stage1_output_usage(...)` 在 memory 被引用后仍正确计数。

### 4. full compaction / auto-compact 验证
- 手动 compact：验证 saved tokens、trigger source、rebuild 状态可见。
- pre-turn auto compact：验证命中阈值后自动触发，且不与 ArkTS fallback 重复。
- model-switch compact：验证切到更小 context window 时走 `maybe_run_previous_model_inline_compact(...)`。
- 失败熔断：连续失败达到阈值后停止自动重试；手动成功后恢复。

### 5. ArkTS / UI 验证
- 在主工作台长会话里观察 token card：能看到 micro / memory / full / circuit 状态变化。
- 重启应用、恢复线程后，`thread/read` 仍能还原最近状态。
- `turn/poll`、event、reconcile 三路最终状态一致，不出现 UI 显示和后端真实状态分叉。

## Recommended implementation order

1. Phase 1：history 元信息 + Layer 1 首批规则
2. Phase 2：host snapshot / thread-read / turn-poll 扩字段
3. Phase 3：ArkTS backend snapshot 承载与三路消费
4. Phase 4：memory 状态透出与尾部保留策略接线
5. Phase 5：full compaction trigger/rebuild 状态透出
6. Phase 6：failure count / circuit breaker / ArkTS fallback 边界
7. Phase 7：Index 页面轻量展示与手动重试收口

这个顺序的核心原因是：当前后端主链已经够强，首版最值得做的是**把已有能力透出来并接稳**，而不是在 ArkTS 上再造一套上下文管理系统。
